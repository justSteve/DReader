### Thesis
- **"Nondeterminism at the edges. Determinism at the core."** This is the takeaway slide, at ~19:07 and not at the end (storyboard). The wide pass placed it at 20:50, which is wrong: 20:46 onward is the Callstack outro.
- **Slop comes from "unstructured delegation."** 03:52, speech-zoom: "where does slop in agents come from? In my opinion, it comes from unstructured delegation … When you tell an agent to basically do everything, you let it do judgment, you give all the structure over to an agent, you let it do all the implementation and taste". The slide at ~03:59 shows You → Agent across a boundary, with Judgment / Structure / Implementation / "Taste" handed over and Slop coming back (storyboard). He is explicitly *not* arguing for micromanaging the agent (04:31, speech-zoom). His objection is that "it works until it doesn't, and when it stops working, what can we actually point to to tell the agent, this is what you need to fix?" (04:40, speech-zoom).
- **Determinism** is "given the same input, you get the same, predictable output every single time" (04:52, speech-zoom; slide at ~04:55, storyboard). In practice it means **the control flow is an explicit state machine, and the LLM fills in content inside states.** Email example (slides ~05:45–06:09, storyboard): the deterministic rules are "Must draft email before sending it / Only send approved emails / Never invent a recipient". The nondeterministic parts are "Email content / Questions asked / Draft revisions made".
- **The framing moved from 2023 to 2026.** In 2023 the question was "Can we constrain agents?" and in 2026 it is "Can we improve agents?" (~03:38, storyboard). A later slide says "2023: The graph keeps the agent honest → 2026: The graph makes the agent better" (~17:50, storyboard). He says the 2023 Agent Conf "was more about constraining agent behavior to state machines" and that today he will show how state machines "improve agent behavior and … remove slop" (03:35–03:42, speech-zoom). **The new claim is that the state machine is the thing you optimise, not only a guardrail.**

### Techniques, in talk order
1. **The mega-prompt anti-pattern (06:28–07:10).** A system prompt carries the control-flow rules ("NEVER call send_email until the user has explicitly approved the latest draft", "Do not make up an email address", "Don't ask too many questions"), and the `send_email` tool description carries a gate ("Only call this after the user approves the draft"). The code shape and the `send_email` lines are storyboard-legible, but the full text is small and is Gemini-read only. His diagnosis, from the zoom (06:44, 07:06): "we're encoding control flow inside the prompt"; "you should never write tools like this where the tool is part of the control flow". Failure list on a slide (~07:31, storyboard, fully legible): ✅ Works (most of the time) / ❌ Can't prove it works / ❌ Can't see how it works / ❌ Can't guarantee it working / ❌ Rules decay w/context / ❌ One prompt = one strategy. On rule decay (07:49, zoom): the rules are "text just like the rest of your context, so as your context builds up, the rules get a little bit less significant over time."
2. **The same agent as an XState machine (08:11–09:00).** Code on the left and the generated diagram on the right. At storyboard level the shape is consistent with Gemini's read: `import { setup } from 'xstate'`, `setup({ guards: { hasRecipient … } }).createMachine({ id: 'email', initial: 'idle', states: { idle: { on: { REQUEST: { target: 'drafting' }}}, drafting: { on: { DRAFTED: { target: 'reviewing' }}} …`. The identifiers themselves are *unread*. The central claim (08:50, speech-zoom): "it's actually mathematically impossible to send an email when you're in … the drafting state or the reviewing state, because there just doesn't exist any transition there." Safety is structural (no edge exists), not a request in the prompt.
3. **Live demo, "Email drafter v1" (09:10–10:30).** The machine was "automatically visualized from a state machine that I or actually an agent wrote" (09:10, speech-zoom). The demo is deliberately clunky. A vague prompt goes to needs-more-info, which asks for the address and subject; he types "Draft anyway"; the draft signs off "Best, [Your name]"; "of course, we forgot the email address"; it finally sends to a simulated outbox (09:20–10:23, speech-zoom). He sets up the clunkiness on purpose: "it's not the best workflow, and that is exactly the point that I'm going to show next" (10:14). The UI label "Stately Agent" and the version tag "XState v0.41 alpha" are *unread*, too small at storyboard size.

    execute(effects)
    while state is active:
        event = nextEvent()
        state, effects = transition(machine, state, event)
        execute(effects)
    return state.output

### Demonstrated vs asserted
- **Demonstrated live:** the XState email agent v1 running with a visualised machine; v2, the agent-proposed machine, running with a shorter path; structured traces (shown as slides, not generated live); and Jev picking the next event on a state machine and recovering from injected faults.
- **Asserted without evidence shown:** that v2 is *better*. No compare-step numbers, eval scores or trace statistics are shown for v1 against v2, so the "Compare" step of his own cycle is not shown. That "at Stately we've done it with our … state machine generation and editing pipeline" (13:42, zoom), with no numbers. That the rules in a mega-prompt "decay with context", which is argued from intuition and not measured. The prior-art citations are named, not discussed.
- **No quantitative evidence anywhere in the talk.** The only numbers are the illustrative trace counters and the Jev UI's confidence figures.

### Analyst section: transfer to Steve's zgent enterprise (Claude's assessment, not the speaker's)
**Transfers well:**
- *Put control flow in structure, not in prompts.* Steve's CLAUDE.md files carry many prompt-level gates of the same kind as the talk's mega-prompt ("No bead = no work", "NEVER execute wsl --shutdown"). Khourshid's "rules decay w/context" argument is exactly why the beads gate works better as a hook or `bd` precondition than as prose. Wherever a rule is a *transition guard* (no commit without a bead id, no push before quality gates, no `wsl --shutdown` without a handoff), encode it where no edge exists: in hooks, formulas or `gc` dispatch. Leave taste and judgment in the prompt.
- *A bead lifecycle is already a state machine* (open → in_progress → closed, with blocked and deferred states; "Silence means Deferred"). Making it explicit (named states, allowed events, guards) would let the enterprise log **transitions as traces**, which is what his "eval the edges" needs. Example edge-level questions: which edges stall (in_progress → nothing), and which cause rework (closed → reopened)?
- *Traces + evals + machine → a separate reviewer agent proposes a revised workflow, constrained by invariants, then A/B the two versions.* This maps onto Gas City formulas (`mol-*.formula.toml`) as the "machine", with an invariants file that no revision may break. His reviewer prompt's constraints are worth copying as written, provided they are first framed at full resolution: "change the workflow, not the prompts or model", and "return the current machine if already fine".
- *Jev + explicit state/event list* is close to the existing `jev-loop` skill's design (deterministic state snapshot, then a judgment model). The talk supports keeping Jev's choices constrained to an enumerated event set.

**Does not transfer, or needs care:**
- Steve's zgents are long-horizon coding and research agents, not narrow workflows like email drafting. Much of their work is the "taste/judgment" region that Khourshid himself leaves nondeterministic, so formalising the whole agent would be ceremony in his own sense.
- XState or Stately tooling itself is not needed. His own point is that a reducer or switch statement over the formula or bead state suffices.
- Self-improving workflows are shown with no measured improvement. Adopt the *Compare* step before trusting any agent-proposed revision.
